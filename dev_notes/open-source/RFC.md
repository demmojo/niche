# RFC: Sovereign Blob Reference Protocol (SBRP)

## 1. Abstract

The Sovereign Blob Reference Protocol (SBRP) defines an OpenTelemetry-compatible standard for ingesting large execution traces (e.g., >100MB LLM contexts) without overwhelming observability data planes. It establishes a secure, asynchronous "Claim-Check" pattern where the compute plane streams raw telemetry directly to tenant-owned blob storage using append-only keys and emits a single, lightweight, immutable OpenTelemetry (OTel) span referencing the blob's ID.

## 2. Protocol Specification

### 2.1 Structural SSRF Elimination & Tenant Authorization

Observability data planes MUST NOT accept full URIs in telemetry payloads. The payload MUST only contain a `blob_id`, an optional `checksum` (SHA-256), and a `storage_route.alias`. These attributes MUST be serialized as flat string keys (e.g., `"sbrp.blob_reference.storage_route.alias"`) and NOT as nested JSON objects to ensure cross-language OTel parser compatibility.

The Data Plane MUST construct the fetch URL internally by mapping the `storage_route.alias` against a server-side whitelist dictionary mapped to a trusted cloud storage endpoint. To prevent Prototype Pollution, this whitelist MUST be instantiated as a prototype-less object (e.g., `Object.create(null)`) or a strict `Map`.

**Cross-Tenant IDOR Mitigation:** The Data Plane MUST enforce a strict, null-safe tenant-bound authorization check: `assert(typeof authenticated_caller_tenant_id === 'string' && whitelist.has(storage_route.alias) && authenticated_caller_tenant_id === whitelist.get(storage_route.alias).owner_tenant_id)`. The `tenant_id` MUST be extracted directly from a verified authentication context (e.g., API Gateway JWT or API key mapping), completely ignoring any untrusted payload attributes. To prevent alias enumeration via information leakage, the API MUST return a generic **HTTP 403 Forbidden** using the schema: `{ "error": "FORBIDDEN", "message": "Storage profile not found or access denied." }` regardless of whether the alias is unrecognized or simply fails authorization.

**Legacy URI Deprecation Contract:** Legacy URIs will be supported until a coordinated API version bump (e.g., `/v2/` endpoints) explicitly removes the schema capability; time-based silent breakages are forbidden. When explicitly rejected, it MUST use the schema `{ "error": "DEPRECATED_FEATURE", "message": "Legacy URIs are no longer supported." }`. However, to eliminate the SSRF window during this period, server-side fetches on legacy URIs MUST be strictly restricted to a pre-populated allowlist of trusted path prefixes (e.g. `https://trusted-storage.com/tenant-bucket/`). The matched legacy URI prefix MUST be explicitly authorized against the `authenticated_caller_tenant_id` to prevent Cross-Tenant Data Injection. The Data Plane MUST parse the legacy URI into a URL object first, resolve/normalize it, and validate the host and path prefix _after_ resolution using exact-match checking to prevent Parser Differential SSRF attacks, Path Traversal bypasses (e.g., `../../`), and SSRF via Shared Cloud Provider Domains. Legacy URIs MUST strictly enforce the `https://` scheme, be validated against an RFC 3986 URL pattern. Legacy URI string evaluations containing any CRLF characters MUST be silently blackholed (returning `200 OK`, dropping server-side, and emitting a security metric) to prevent both HTTP Response Splitting and infinite retry loops (CRLF rejection MUST NOT be applied to the entire JSON body, as that breaks valid string contexts). Unlisted legacy URIs MUST be "blackholed" (silently dropped server-side while returning `200 OK` to the client) to prevent infinite retry loops in older SDKs lacking circuit breakers, and MUST emit a dedicated internal security metric (e.g., `sbrp.security.ssrf_sink_count`) to prevent auditing blindspots.

### 2.2 Immutable Telemetry & Distributed Scalability

To eliminate the distributed coordination bottleneck, the protocol mandates **UUIDv7** for the `blob_id`.

- **Object Storage Hot Partition & IDOR Prevention:** The storage path MUST include the high-entropy shard prefix using SHA-256 at the very beginning to prevent upfront storage partitions, followed by the tenant namespace (which MUST be validated against strict alphanumeric boundaries e.g., `^[a-zA-Z0-9_-]+$` to prevent Path Traversal), and a time-bound hierarchy deterministically derived from the UUIDv7's embedded 48-bit Unix timestamp (MUST be evaluated in UTC to prevent boundary skew): `{SHA-256(UUIDv7)[0:4]}/{tenant_id}/YYYY/MM/DD/HH/{UUIDv7}`.
- **Immutable Spans & Persistent Outbox:** The Compute Plane MUST await confirmation of successful blob persistence _before_ emitting the OTel trace via a **Transactional Outbox**. The outbox MUST NOT mandate durable local storage dependencies (like container volumes); it should accept a generic local filesystem path or an `OutboxStore` interface to maintain serverless compatibility (e.g., FaaS environments like serverless functions). If utilizing a local filesystem path, the implementation MUST enforce strict POSIX file permissions (e.g., `chmod 0700` or `0750` for directories, `0600` for files) on the Outbox directory and its contents to prevent Sensitive Data Exposure of LLM contexts to unprivileged processes. Furthermore, local file integrity checks (e.g., checksum validation) MUST be performed prior to transmission to detect corruption at rest.
- **"Poison Pill" Dropping & Metrics:** Outboxes MUST explicitly drop and NEVER retry terminal client errors (`VALIDATION_ERROR`, `FORBIDDEN`, `PAYLOAD_TOO_LARGE`, `DEPRECATED_FEATURE`). The outbox MUST NOT infinitely retry if an ingress proxy returns a non-JSON HTML 4xx terminal error (e.g., 400, 401, 403, 413), but MUST explicitly exempt transient HTTP 429 and HTTP 408 responses to ensure rate-limits and network timeouts correctly trigger exponential backoff rather than dropping data. The outbox MUST enforce a strict `max_capacity` (FIFO drop) or TTL to drop the oldest spans during sustained backend queue backpressure (e.g. 429s). The SDK MUST delegate drop counting to standard OTel `Meter` mechanisms (e.g., `counter.add(1)`) rather than defining a custom SBRP-specific metric batching loop.
- **Data Plane Idempotency & Sweeper:** The DB enforces `INSERT ... ON CONFLICT (blob_id) DO UPDATE SET status = 'PENDING', checksum = EXCLUDED.checksum, storage_route_alias = EXCLUDED.storage_route_alias, updated_at = NOW() WHERE table_name.tenant_id = EXCLUDED.tenant_id AND (table_name.status = 'FAILED' OR (table_name.status = 'PROCESSING' AND table_name.updated_at < NOW() - INTERVAL '5 minutes'))`. For legacy full payloads lacking a `blob_id`, the Data Plane MUST generate a deterministic surrogate `blob_id` (e.g., SHA-256 hash of the payload or URI) server-side to utilize the exact same state machine. The Data Plane enqueues the background worker and utilizes a state machine (e.g., `PENDING`, `PROCESSING`, `VALIDATED`, `FAILED_TERMINAL`) with atomic `UPDATE ... WHERE status = 'PENDING'` queries to acquire the task. The state machine update query MUST utilize a limit clause and row-level locking (e.g., `FOR UPDATE SKIP LOCKED`) to prevent worker lock contention and OOM starvation. All database queries MUST strictly utilize parameterized queries or prepared statements; string interpolation is strictly forbidden. Because clients receive an immediate asynchronous `202 Accepted` and discard the telemetry span, they cannot retry upon background worker failures. Therefore, the Data Plane MUST implement an internal background sweeper (cron job) with a `LIMIT` clause to process in paginated batches, which periodically re-enqueues payloads stuck in a transient `FAILED` state (like HTTP 404s due to eventual consistency, which MUST NOT be treated as terminal) or stale `PROCESSING` locks. The sweeper (and ONLY the sweeper) MUST increment the `retry_count` during this transition to prevent client network retries from artificially exhausting the budget. Any payload encountering a deterministic failure (e.g., permanent checksum mismatch, JSON parsing error, corrupted data) or exceeding a hard `max_retries` cap MUST be marked as `FAILED_TERMINAL` to prevent infinite poison-pill retry loops.
- **Orphaned Blob Garbage Collection & Lifecycle:** The Data Plane requires only `Blob Storage Read` permissions. Lifecycle management (e.g., removing the 72-hour TTL via Object Tagging) MUST be handled entirely by the Compute Plane or the Sovereign Storage configuration.

### 2.3 Ingress Edge Protection: Pre-Signed POST Policies

If the Compute Plane utilizes Pre-Signed POST URLs for blob uploads, the tenant's own authorization backend MUST generate them. All Pre-Signed POST requests MUST include a `content-length-range` policy, strict `Content-Type` whitelist (explicitly forbidding execution-capable MIME types like `image/svg+xml`, `text/html`, or `application/pdf`), and exact `key` equivalence. For POST request generation, the tenant backend MUST verify the requested path strictly conforms to the tenant's namespace format (e.g., verifying the `{tenant_id}` segment after the high-entropy shard), and MUST generate a unique UUIDv7 `blob_id` server-side to guarantee collision avoidance, mitigating Pre-Signed POST IDOR and blob overwriting attacks. The Observability Data Plane DOES NOT generate these POST URLs and maintains its strict Read-Only privileges.

**Client-Side UI Fetching & Stored XSS Mitigation:** Observability UIs MUST use a read-only **Pre-Signed GET URL**. To prevent Stored XSS, Object Storage buckets MUST enforce strict `Content-Type` mapping upon upload. Furthermore, all Pre-Signed GET URLs MUST inject `response-content-disposition=attachment` and `response-content-type=application/octet-stream` (or `application/json`) to force a download and prevent inline browser execution of malicious media types. The UI Proxy Fallback mechanism is explicitly rejected (YAGNI). The Observability UI MUST enforce strict context-aware output encoding (e.g., modern template engines) when rendering blob contents to prevent Stored XSS, and MUST implement stream parsing with strict client-side rendering truncations (e.g., capping rendered DOM output to 5MB) to prevent Client-Side DOM OOM (Browser DoS). All API endpoints generating Pre-Signed URLs (GET) MUST assert strict tenant authorization against the database record (`authenticated_user_tenant_id === target_blob.tenant_id`) and explicitly verify the blob is `VALIDATED` (or equivalent positive state check, explicitly not just "not FAILED") before cryptographic signing to prevent Cross-Tenant IDOR, corrupted data delivery, and race conditions during 202 async ingestion. Object Storage buckets MUST enforce strict CORS policies, restricting `AllowedOrigins` strictly to authorized Observability UI domains.

### 2.4 HTTP Fetch Behavioral Contract (Data Plane)

1.  **202 Async Ingestion:** The Data Plane MUST immediately return **HTTP 202 Accepted** upon synchronously validating the schema of the OTel span for both SBRP and valid legacy payloads. Invalid legacy full payloads MUST still be synchronously rejected with **HTTP 400 Bad Request** to maintain backward compatibility for error handling. The API Gateway MUST enforce standard proxy ingress limits (e.g., 5MB) for all synchronous ingestion paths, rejecting oversize payloads with HTTP 413. Only valid legacy full payloads within this ingress limit MUST be routed into a dedicated, isolated background queue that cannot starve the primary ingestion path to prevent Application-Layer DDoS.
2.  **Worker Connection Starvation Prevention:** Background workers MUST pass a strict socket timeout to the DB driver.
3.  **Queue-Depth SLOs & Tenant Limiting:** The background worker queue MUST enforce Tenant-Bounded Rate Limiting and a strict **`max_queue_depth`** per tenant. If the depth is exceeded, the API MUST reject new SBRP spans synchronously with **HTTP 429 Too Many Requests** (using the schema: `{ "error": "TOO_MANY_REQUESTS", "message": "Tenant queue capacity exceeded." }`). Valid legacy SDKs exceeding backend limits MUST also receive HTTP 429; blackholing with `200 OK` is reserved strictly for unauthorized/unlisted legacy URIs. Generic L7 rate limiting MUST apply globally before the payload reaches the SBRP application layer to prevent CPU starvation.
4.  **Anti-Tarpitting (Slowloris):** The client MUST enforce a strict absolute timeout (e.g., **15-30 seconds**).
5.  **Decompression Bomb (OOM) Protection:** The Data Plane MUST mandate a strict `max_download_size` on the incoming HTTP fetch socket (e.g., 50MB) for the compressed stream, aborting immediately if the `Content-Length` header or tracked raw bytes exceed this limit to prevent Bandwidth Exhaustion. Additionally, it MUST enforce a strict byte-read limit on the **uncompressed** stream (e.g., 250MB), cap the maximum decompression ratio (e.g., 100:1), and enforce a strict execution timeout on the decompression stream itself to prevent CPU starvation. If any of these limits are exceeded during the background worker fetch, the worker MUST update the database record to a terminal `FAILED_TERMINAL` state, log the failure server-side, and emit a metric. The synchronous **HTTP 413 Payload Too Large** response (schema: `{ "error": "PAYLOAD_TOO_LARGE", "message": "Payload size exceeded ingress limits." }`) MUST ONLY be used if the initial lightweight OTel span payload itself exceeds the proxy ingress limits.
6.  **Payload Integrity:** The background worker MUST verify the `sbrp.blob_reference.checksum` (if provided) using non-blocking, streamed chunk-based cryptographic hashing. The protocol strictly pins the checksum algorithm to SHA-256; implementations MUST reject any payloads attempting to negotiate weaker or null ciphers (e.g., MD5, CRC32). The background worker MUST buffer the parsed trace or explicitly defer the downstream datastore commit operation until the checksum hash stream fully resolves and validates at EOF, preventing corrupt data from being committed. If checksum validation fails or the payload is unparseable (e.g. non-JSON garbage), the worker MUST update the database record to a terminal FAILED state rather than rejecting synchronously, ensuring the UI state remains consistent. The API MUST implement a Penalty Box / circuit breaker that temporarily restricts tenants who trigger multiple deterministic failures (including checksum mismatches or unparseable non-JSON garbage) within a sliding time window (by synchronously rejecting new payloads with HTTP 429 Too Many Requests to apply backpressure so the client retries after the penalty expires, rather than destroying data permanently).
7.  **Dynamic Concurrency & Strict Concurrency Limits:** The Data Plane MUST utilize Strict Concurrency Limits with high/low watermarks (e.g., using bounded worker pools and semaphore-based concurrency limits) to maximize concurrent fetches while preventing OOM crashes and GC thrashing.
8.  **High-Performance Parsers:** The worker MUST use high-performance streaming JSON parsers with bounded memory limits.

### 2.5 Telemetry Parsing & Log Forging Protections

Telemetry middleware MUST explicitly reject payloads containing unsafe ASCII control characters (`[\x00-\x08\x0B\x0C\x0E-\x1F\x7F]`) OR Unicode separators.
