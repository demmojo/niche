# Technical Philosophy of SBRP

The Sovereign Blob Reference Protocol (SBRP) is anchored on four absolute technical principles: Zero Trust, Append-Only Immutable Ledgers, Open Standards, and Immutable Telemetry Events.

## 1. Zero Trust: The Ingress Edge and SSRF

A foundational philosophy of SBRP is that no URI provided by an agent or external compute engine can be implicitly trusted.

- **The Origin Isolation:** The storage provider MUST mandate a sandbox domain separate from the primary application logic, relying on `nosniff` headers and `Content-Disposition: attachment` to neutralize MIME-spoofing and Polyglot files (e.g., GIFAR).
- **The Abstraction Boundary:** All URL resolution MUST be strictly hardcoded. The protocol mandates stripping user-provided URIs entirely from the schema, relying solely on interpolating a `blob_id` and a server-whitelisted `storage_route.alias` into a trusted endpoint template. The whitelist resolution MUST enforce cross-tenant authorization boundaries by ensuring type-safe comparisons (`assert(typeof authenticated_caller_tenant_id === 'string' && whitelist.has(storage_route.alias) && authenticated_caller_tenant_id === whitelist.get(storage_route.alias).owner_tenant_id)`). The client operates under the philosophy that all redirects are hostile, strictly enforcing `follow_redirects: false` to neutralize SSRF via routing rules.
- **Authentication Boundary:** The Data Plane MUST authenticate all GET requests (e.g. cloud provider signature algorithms), allowing data owners to enforce "Block Public Access" policies on their buckets. Pre-Signed POST requests for trace uploading MUST be explicitly generated by the tenant's own authorization backend (verifying prefix boundaries and generating UUIDv7 keys server-side) rather than by the Data Plane, preserving the Data Plane's strictly read-only role and neutralizing Cross-Tenant IDOR and blob overwrites.
- **Anti-Tarpitting & Resource Bounding:** The client dynamically bounds all concurrent fetches based on available memory, limits uncompressed byte reads to prevent Zip Bombs, and enforces Idle Timeouts to prevent Slowloris and connection pool exhaustion from eagerly resolved telemetry payloads.

## 2. Append-Only Immutable Ledgers: Eliminating Write-Contention

In a distributed architecture streaming 100MB+ multimodal context windows, synchronous HTTP telemetry ingestion guarantees failure. Traditional mutation-based storage patterns fail under high-throughput concurrent loads.

- The philosophy mandates an **Append-Only Immutable Ledger** for sovereign blob storage (e.g., Object Storage).
- Data is written utilizing UUIDv7 entropy keys (prefixed with high-entropy shards to prevent hot partitions).
- By preventing trace mutation, we structurally eliminate write-contention.
- The compute engine streams the raw context asynchronously, and only after ensuring persistence does it emit the OpenTelemetry `sbrp.blob_reference` payload. Storage bloat from crashes is managed via bucket Object Lifecycle Management (OLM) TTLs.

## 3. Open Standards: OpenTelemetry (OTel)

We refuse to build vendor-locked telemetry pipelines or implement language-specific workarounds. The SBRP represents an explicit schema designed natively for the Cloud Native Computing Foundation (CNCF) OpenTelemetry specification.

- By strictly typing `sbrp.blob_reference.blob_id` (UUIDv7), SBRP forces standard compliance across any observability dashboard.
- By mandating the explicit rejection of all unsafe ASCII control characters (`[\x00-\x08\x0B\x0C\x0E-\x1F\x7F]`) and Unicode separators (`\u2028`, `\u2029`, `\u0085`) at the boundary, the protocol aggressively guards against Log Forging, CRLF injection, and downstream Schema Desynchronization. Legacy payloads containing any CRLF sequences (`\r`, `\n` used improperly for headers) MUST trigger an immediate HTTP 400 rejection across all implementations, explicitly preventing HTTP Response Splitting. While safe newlines (`\n`) within the JSON payload bodies themselves are preserved, they MUST be strictly encoded by the parsing engine.

## 4. Immutable Telemetry Events

To ensure correctness in a heavily concurrent Kubernetes environment without complex state machine updates, the philosophy demands strict event immutability.

- UUIDv7 embeds a high-precision timestamp, allowing highly distributed orchestration swarms to generate keys concurrently without centralized locking mechanisms.
- OpenTelemetry spans are fundamentally immutable point-in-time events. By awaiting confirmation of blob persistence before emitting the span, SBRP eliminates race conditions and complex state transitions on the backend. This cleanly models the true lifecycle of an asynchronous, persistent claim-check event.
