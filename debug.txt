   - **Progressive Fetch Pattern:**

#### Rate Limiting & DoS Mitigation
 Never use generic spinners for long-running AI tasks. Implement a two-stage architecture: Phase 1 (`Initial Fetch Phase`) fetches fast, deterministic data (e.g., Exa search results, <2s) to immediately satisfy user intent. All Phase 1 endpoints MUST be subject to standard IP-based or user-based rate limiting (HTTP 429) to prevent basic API abuse. **Performance Guardrail (Rate Limit Storage):** All Phase 1 rate limit tracking MUST use Redis or a similar distributed cache. Explicitly ban the use of Firestore for tracking rate limits, as this will trigger the Firestore 1 write/sec per document limit and cause immediate `DEADLINE_EXCEEDED` bottlenecks. **Migration Guardrail:** Applying new HTTP 429 rate limits to legacy `/v1/` endpoints introduces a breaking behavioral contract change, but you MUST NOT leave them unmetered. You MUST apply a 'permissive but protective' infrastructural rate limit ceiling on legacy `/v1/` routes (e.g., 99.9th percentile of historical traffic) to prevent severe Financial DoS and volumetric abuse. Stricter, application-level rate limits MUST be exclusively enforced on the `/v2/` namespace. Furthermore, the backend MUST return standard rate limit headers (`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `Retry-After`) in the response so clients can adapt dynamically.

#### Authentication & Tenant Isolation
**Security Guardrail (SSRF & Authz):** All endpoints MUST verify backend authorization. This MUST verify BOTH tenant boundaries (`workspaceId` matching) AND user permissions/roles (e.g., `role === 'admin'`) to prevent Broken Access Control (BOLA), just like Phase 2. **Security Guardrail (Strict Tenant Isolation):** For `/v2/` routes, enforce strict `workspaceId` matching. For legacy `/v1/` routes, you MUST explicitly enforce intrinsic isolation to prevent Broken Object Level Authorization (BOLA). Migrate legacy keys to a strict mapping table (`authorizedWorkspaces`) and assert that the requested `workspaceId` is within this list.

#### Database Efficiency & Pagination
**Database Efficiency Guardrail:** All Phase 1 database reads MUST use exact point-reads or range queries fully covered by composite indexes, and ALL range queries MUST enforce strict `LIMIT` clauses or cursor-based pagination to prevent Node.js OOM crashes. **Database Efficiency Guardrail (Pagination):** Explicitly ban the use of `.offset()` in Firestore queries, as it forces O(N) read costs and latency; pagination MUST use O(1) `.startAfter()` document snapshots. Strictly forbid N+1 query patterns. To prevent NoSQL injection, explicitly mandate that all Firestore query operators and field paths MUST be strictly hardcoded on the backend; user input MUST ONLY be passed as the query value.

#### SSRF Defenses
Phase 1 fetches of external data MUST implement strict Server-Side Request Forgery (SSRF) mitigations, mandating the use of a robust, actively maintained SSRF prevention library that comprehensively blocks all private, link-local, loopback, and broadcast IP spaces across both IPv4 and IPv6 protocols after DNS resolution (enforcing IP Pinning to prevent DNS Rebinding TOCTOU attacks). **Security Guardrail (SSRF Auto-Redirects):** Standard HTTP clients automatically follow redirects, which bypasses IP pinning. You MUST explicitly disable automatic redirects (`redirect: 'manual'` in fetch). If redirects are required, the backend MUST intercept the `Location` header, resolve the new host, and recursively pass the new IP through the exact same SSRF blocklist validation, enforcing a strict hard limit on redirect depth (e.g., maximum 3 redirects) to prevent infinite loops and Server-Side DoS. Furthermore, to prevent credential leakage to external attacker-controlled domains, the HTTP client MUST explicitly drop `Authorization`, `Cookie`, and all custom authentication headers when following a redirect to a different origin. To prevent breaking TLS Server Name Indication (SNI), do NOT alter the outbound URL to use the raw IP address. Instead, implement strict IP Pinning. Because standard `fetch` with pre-flight URL validation is vulnerable to DNS Rebinding TOCTOU attacks on socket creation, you MUST explicitly mandate the use of a custom `http.Agent` or `undici.Dispatcher` (which robust Node.js SSRF libraries use under the hood). This intercepts socket creation, validates the IP against the blocklist, and connects directly to the evaluated IP output from the validator without allowing the HTTP client to re-parse or re-resolve the original hostname, preventing SSRF bypasses via URL parsing discrepancies. **Security Guardrail (URI Scheme Validation):** For `/v2/`, the SSRF mitigation MUST strictly enforce that only the `https://` scheme is allowed. For legacy `/v1/` routes, explicitly use a strict Allowlist (`https://` and conditionally `http://` for local development only), completely rejecting all other schemes like `data:`, `ws:`, `javascript:`, `file://`, `gopher://`, `dict://`. This prevents severe local file reads, internal port scanning, and direct payload injection via `data:text/plain;base64,...`.

#### Input Validation, Prompt Injection & Mass Assignment
**Security Guardrail (Prompt Injection & Validation):** All standard user inputs and form submissions must be validated via a strict schema library (like `Zod`) at the backend boundary before processing. To prevent prompt injection, explicitly mandate using regex `replace(/[<>]/g, "")` to sanitize inputs before passing them to LLMs, as instruction-tuned LLMs actively auto-decode entities. **Security Guardrail (ReDoS Mitigation):** Zod schemas MUST enforce hard string length limits (`.max()`) on ALL text fields BEFORE any regex validation occurs to mitigate ReDoS (Regular Expression Denial of Service) attacks. Because Zod does not short-circuit chained string validations by default, you MUST use `.pipe()` (e.g., `z.string().max(100).pipe(z.string().regex(/.../))`) to force an early return if the length limit is exceeded. We mandate a custom ESLint rule that fails CI builds if `.regex()` is called on a Zod string without a preceding `.pipe()` chain. **Migration Guardrail:** Banning the use of permissive schemas (e.g., using `.passthrough()`) is strictly enforced on `/v2/` routes. However, legacy `/v1/` routes MUST NOT migrate to strict schemas at the gateway layer, as this breaks legacy contracts. For `/v1/`, use `.passthrough()` with shadow validation to log extraneous payload keys. However, the Data Access Layer (DAL) MUST NEVER accept this permissive `/v1/` object directly. The Controller MUST explicitly map the permissive `req.body` into a strict internal domain object before interacting with the DAL, eliminating the Mass Assignment vulnerability. **Security Guardrail (Prototype Pollution):** Use a natively secure JSON parser (e.g., `secure-json-parse`) before Zod parsing, and explicitly mandate that the backend MUST reject `application/x-www-form-urlencoded` content types entirely (or configure the `qs` middleware with `allowPrototypes: false`), to prevent deep prototype pollution bypasses on permissive legacy routes. **Security Guardrail (Mass Assignment):** For `/v2/` routes, validation MUST run strictly with `.strip()` to drop extraneous keys. However, for legacy `/v1/` routes, you MUST explicitly preserve permissive `.passthrough()` behavior to prevent breaking API contracts. `/v1/` routes must use pure "Shadow Validation" (logging deviations without mutating the payload) to preserve the exact legacy contract until full deprecation. For `/v2/`, the payload stripping MUST be enforced at the Controller perimeter. For `/v1/`, preserve permissive passing to avoid breaking contracts.

#### Background AI & Data Sanitization
Furthermore, any third-party data fetched in `Initial Fetch Phase` must be strictly sanitized. To prevent Event Loop Starvation during this sanitization, enforce strict `Content-Length` checks and stream truncation (e.g., 100KB limit) *prior* to running any string-parsing defenses. Wrap the truncated payload in **Randomized Boundary Delimiters** generated dynamically per-request. Mandate cryptographically secure 256-bit entropy (e.g., `crypto.randomBytes(32).toString('hex')`) for these delimiters. The backend MUST implement a `.includes()` assertion to verify that the generated delimiter string does not naturally exist within the fetched third-party payload before concatenation, mathematically preventing prompt injection breakouts. Do not rely solely on HTML-entity encoding, as instruction-tuned LLMs actively auto-decode entities before semantic processing, making static tags vulnerable to breakout. Prefer using native LLM Provider Data/Context separation APIs (e.g., Gemini's `system_instruction` vs. user payload) to enforce isolation. `Streaming Phase` kicks off background AI logic. **Security Guardrail (Authz & Financial DoS):** All generative endpoints MUST first verify strict backend authorization (e.g., explicitly asserting that the requested resource's `workspaceId` and the token's `workspaceId` are defined, non-empty, and strictly match, AND checking RBAC roles) BEFORE any Token Bucket deduction or LLM invocation occurs. 

#### Network Security, CORS & Threat Monitoring
**Security Guardrail (Threat Monitoring & Data Exposure):** The backend MUST asynchronously log the full security context using **structured JSON logging** (e.g., `pino` or `winston`) to escape control characters and prevent CRLF log forging. Dispatch logs via `stdout` for Cloud Logging or a non-blocking queue like Pub/Sub, rather than synchronously writing to the primary database, preventing connection pool exhaustion during a volumetric Layer 7 DoS. It must log the full security context (User ID, IP, headers, target URL) for any Authz rejection, SSRF block, or Rate Limit trigger, correlating it with the `traceId`. **Crucially, all sensitive headers (e.g., `Authorization`, `Cookie`, `X-Api-Key`) MUST be explicitly redacted or omitted before logging to prevent credential theft.** **Security Guardrail (Network & CORS):** IP-based rate limiting MUST securely resolve client IPs by explicitly configuring the reverse proxy trust boundary (e.g., verifying the Cloudflare/GCP Load Balancer IP ranges using an array of trusted subnets in Express' `trust proxy` or securely reading edge-verified headers like `CF-Connecting-IP`), ignoring arbitrary user-supplied `X-Forwarded-For` spoofing. Avoid hardcoded proxy depths (`trust proxy: 1`) if the infrastructure utilizes multiple layered proxies. Additionally, the backend MUST enforce strict CORS policies, explicitly whitelisting the permitted frontend domains and rejecting `null` or wildcard origins for authenticated routes. To prevent inbound payload OOM attacks, all endpoints MUST enforce strict maximum request body sizes (e.g., `100kb` for JSON) at the web server or middleware layer. **Security Guardrail (Tarpitting):** Implement progressive delays (Tarpitting) or temporary IP bans via WAF for clients that repeatedly hit rate limits or fail Authz checks. However, explicitly exempt Authz failures caused by the `SKEW_TOLERANCE_SECONDS` JWT lockout window from triggering WAF bans, to avoid permanently banning legitimate users who automatically retry.

#### JWT Revocation & Redis Infrastructure
**Security Guardrail (Revocation Latency):** To eliminate the 1-hour JWT expiration window, implement a high-performance Token Revocation Blocklist in Redis. Check the user's JWT `auth_time` claim against a Redis `revokedBefore` timestamp for that `uid`. To safely trap tokens, the mathematical evaluation MUST strictly check `auth_time < revokedBefore` (strictly less than, using precise millisecond timestamps if possible). Do NOT attempt to artificially skew `auth_time` into the future during re-authentication, as this violates JWT RFCs and causes `TokenUsedBeforeError` rejections by strict validators like Firebase Admin. Instead, ensure the re-authentication process issues the new JWT with an `auth_time` that is at least equal to the `revokedBefore` timestamp, and that the strict `<` evaluation allows it to pass. Because Firebase Auth lacks an `onDisable` trigger, native console revocations will NOT synchronize to Redis, leaving disabled users with active access. You MUST implement a dedicated internal Admin API endpoint for user offboarding that synchronously writes to the Redis blocklist. Explicitly document and forbid using the native Firebase Console for emergency offboarding. Furthermore, explicitly mandate that Redis revocation keys use an absolute TTL mathematically equal to the JWT maximum lifetime (e.g., 3600 seconds), and explicitly mandate `maxmemory-policy volatile-ttl` for the Redis instance handling security blocklists, ensuring that keys have TTLs strictly matched to their corresponding JWT expiries. Do NOT use `noeviction`, as it causes failed writes when memory is full, locking out administrators from revoking active attacker tokens (fail-open scenario). Do NOT rely on checking the `iat` claim, as background token refreshes generate new `iat` timestamps while preserving the original `auth_time`, allowing an attacker to bypass the blocklist without re-authenticating. Do NOT rely on synchronous Firestore `UserRecord` reads for this hot path, and do NOT rely solely on documented administrative policies. **Security Guardrail (Token Bucket Fallback):** If Redis is unreachable (timeout > 20ms), the Token Bucket MUST fail-closed for anonymous/free-tier traffic to prevent Layer 7 DoS and financial exhaustion, Because the security posture demands strict fail-closed for Authentication (rejecting all JWTs when Redis is down), an in-memory `lru-cache` Token Bucket fallback for authenticated traffic becomes unreachable dead code. Remove the mandate for the `lru-cache` fallback entirely; if Redis is unreachable, the system MUST completely fail-closed, resulting in a Denial of Service for all authenticated traffic, prioritizing security over availability. Do not maintain complex math abstractions or duplicate stateful algorithms. **Performance Guardrail (Redis Separation):** To eliminate network latency, evaluate the Redis Revocation Check and the Token Bucket decrement sequentially but asynchronously (e.g., `Promise.all()`) if possible, prioritizing the Revocation check. Do NOT attempt to combine the identifiers into a unified hash tag to execute atomically in a single pipelined Lua script, because Rate limit tracking and Security/Authz blocklists MUST be physically or logically separated (e.g., separate Redis instances or logical DBs) to prevent a volumetric Layer 7 DoS from forcefully evicting older JWT revocation keys. **Performance Guardrail (Lua Complexity):** The Lua script MUST avoid any JSON serialization/deserialization (`cjson.encode/decode`) and strictly use basic native operations (`HGET`, `INCRBY`, `EXPIRE`) to maximize Redis ops/sec throughput on its single thread. This Lua script MUST have an **O(1) Time Complexity**, strictly avoiding any iterations or loops that would block the single-threaded Redis engine.

#### Frontend Stream Resumption & Error Handling
Do NOT use Firestore inline transactions for this synchronous path. If `REST API Fetch` is a single deterministic result, replace UI shimmers asynchronously via React 19 `<Suspense>`. If the background logic is a continuous generative stream, defer to the SSE Streaming Architecture. Catch errors using targeted, localized `<ErrorBoundary>` components as sibling wrappers around the `<Suspense>` blocks so that a failure gracefully degrades into a Partial error interface without destroying valid `REST API Fetch` data. We explicitly deprecate the anti-pattern of subverting `use()` unwrapping by forcing Promises to resolve to `{ data, error }` objects. You MUST differentiate `AbortError` sources at the point of consumption or inside your localized fetch utility. Since both unmounting and intentional cancellation trigger an identical `AbortError`, the implementation MUST pass a custom `DOMException` to the abort call (e.g., `abortController.abort(new DOMException('byte_limit_exceeded', 'AbortError'))`) and check `err.name === 'AbortError' && err.message` in the catch block to explicitly differentiate security limits from user cancellations. If the reason is 'user_cancel' and the length flag is true, return a `Partial` error state. Only ignore `AbortError`s explicitly triggered by component unmounting (`err.message === 'unmount'`). For intentional user cancellations (e.g., clicking a 'Stop' button), the application MUST transition to a 'Cancelled' or 'Partial' state to provide UI feedback, rather than silently swallowing the error. **Implementation Detail (Reconnection Idempotency):** The SSE network lifecycle MUST explicitly require clients to pass a `Last-Event-ID` or `ResumptionToken` header upon `AbortController` recovery/reconnection. **Security Guardrail (IDOR/BOLA):** This stream resumption endpoint MUST NOT blindly trust the `ResumptionToken`. The `ResumptionToken` MUST be a high-entropy cryptographically signed token or securely mapped in a server-side cache. If verifying an HMAC token (e.g., `HMAC-SHA256`), the signed `ResumptionToken` payload MUST embed a strict expiration timestamp (`exp` claim, e.g., max 5 minutes). Do NOT use a strict single-use `jti` nonce that is burned immediately upon connection, as this creates a race condition where clients are permanently locked out if the network drops before they receive a new ResumptionToken. Instead, rely on the strict short `exp` claim and validate the `Last-Event-ID` offset. Do NOT implement heavy, distributed explicit concurrency locks (e.g., Redis active socket tracking) solely to prevent multi-tab interleaving, as this introduces severe operational coupling to the stateless SSE layer. Instead, rely entirely on short token expirations and strict client-side offset validations. Furthermore, the backend MUST explicitly verify that `bufferA.length === bufferB.length` before using a constant-time comparison function (e.g., `crypto.timingSafeEqual`) to prevent fatal `TypeError` DoS crashes on mismatched lengths. Furthermore, the backend MUST re-execute the exact same authorization assertions before piping the cached stream to prevent cross-tenant hijacking. Because backend LLM processes are aborted upon client disconnect to prevent runaway compute costs, stream resumption requires partial re-prompting or resuming from the last checkpointed state. The resumption endpoint must handle graceful recovery without assuming the generation finished in the background. **Strict Hook Encapsulation:** The `useGenerativeStream` hook MUST completely encapsulate `isCancelled` unmount tracking, stream throttling, and promise unwrapping. Consuming components MUST receive a pure, declarative state object and should never manually track `AbortController` lifecycles or internal catch blocks. For all other errors, degrade gracefully into a standardized `Partial` error interface. **Security Guardrail (Information Disclosure):** Native `Error` objects must NEVER be passed directly to the frontend state, as they can serialize backend stack traces or API keys. They must be mapped to a sanitized `ApiError` interface (e.g., `{ status: 'partial_error', details: string, code: string, traceId: string }`). The architecture MUST mandate appending a unique `traceId` to the `ApiError` payload, enabling engineers to correlate the opaque UI error with the exact backend logs. Furthermore, explicitly evict aborted promises from any `use()` Promise Cache to prevent rendering stale aborted states on remount.
