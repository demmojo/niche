# RFC v14: LangSmith Multiplexing Protocol - Zero-Trust Claim Checks & Tenant Isolation

**Date:** April 11, 2026  
**Status:** Proposed  
**Author:** Security Sentinel

## 1. Context & Motivation

RFC v13 successfully stabilized the pipeline against resource exhaustion and split-brain failures through `stream.pipeline`, TTLs, Monotonic Fencing Tokens, and server-side clocks.

However, a strict security audit of the v13 architecture reveals critical vulnerabilities in the **Claim Check** handoff and **Worker Execution** phases:

1. **IDOR on Claim Checks:** Returning a raw UUID (`blobId`) as a Job ID allows attackers to poll or access asynchronous job results if they leak or guess another tenant's UUID.
2. **Confused Deputy in Storage (Flat Namespace):** Blobs are stored in a flat `ingestions/` directory. Workers operate with global bucket permissions. A manipulated message or path traversal vulnerability could trick a worker into processing Tenant A's blob and saving the results into Tenant B's database.
3. **Unbound Authorization Context:** The background worker trusts the Cloud Task payload implicitly, lacking cryptographic proof that the `blobId` was actually generated by the claimed `tenantId` during ingress.

This RFC (v14) resolves these vulnerabilities by introducing **Cryptographically Bound Claim Checks**, **Tenant-Scoped Storage Namespaces**, and **Worker Downscoping (STS/Pre-Signed URLs)**.

## 2. Goals & Non-Goals

**Goals:**

- Eradicate IDOR vulnerabilities on asynchronous polling and claim checks.
- Cryptographically bind uploaded payloads (blobs) to the authenticated tenant.
- Prevent Confused Deputy attacks by revoking the worker's global Cloud Storage IAM permissions.
- Enforce strict tenant isolation at rest.

**Non-Goals:**

- Changing the stream pipeline or fencing token idempotency mechanisms from v13.

## 3. Security Architecture & Fixes

### 3.1 Tenant-Scoped Storage Namespaces

**Vulnerability:** A flat `ingestions/` namespace allows lateral movement if a worker is compromised or tricked via path traversal (`../../tenantB/secret.json`).

**Fix:** Cloud Storage paths MUST be strictly namespaced by the authenticated `tenantId`.

```javascript
// At HTTP Ingress (req.user.tenantId is verified via Firebase Auth / custom middleware)
const tenantId = req.user.tenantId;
const blobId = crypto.randomUUID();

// Strict Namespacing
const filePath = `ingestions/tenants/${tenantId}/${blobId}.json`;
const file = bucket.file(filePath);
```

### 3.2 Cryptographically Bound Claim Checks (JWT)

**Vulnerability:** Returning `{ jobId: "uuid" }` is an unbound token. It carries no proof of ownership.

**Fix:** The HTTP Ingress must return a Signed Claim Check. We use an HMAC-signed JWT (or authenticated encryption like AES-GCM) to bind the `blobId` to the `tenantId`.

```javascript
// Generate the Cryptographic Claim Check
const claimCheck = jwt.sign(
  {
    blobId: blobId,
    tenantId: tenantId,
    exp: Math.floor(Date.now() / 1000) + 60 * 60, // 1 hour TTL
  },
  process.env.CLAIM_CHECK_SECRET,
);

// Return to client
res.status(202).json({
  status: "Accepted",
  jobId: claimCheck, // The client uses this token to poll for status
});
```

When the client polls `/api/v1/jobs/:jobId`, the server verifies the JWT signature and ensures `req.user.tenantId === decoded.tenantId`. This makes IDOR mathematically impossible.

### 3.3 Mitigating the Confused Deputy: Pre-Signed URLs & STS Downscoping

**Vulnerability:** Background workers running on Cloud Run traditionally use a Service Account with `roles/storage.admin` or `roles/storage.objectViewer` across the _entire_ bucket. If an attacker injects a malicious task into the queue, the worker will gladly read any file in the bucket.

**Fix:** Implement the Principle of Least Privilege using one of two methods (Pre-Signed URLs preferred for simplicity).

#### Preferred: Ephemeral Pre-Signed URLs

The Ingress server generates a short-lived, read-only Pre-Signed URL scoped _exclusively_ to the specific blob. The background worker receives this URL in the Cloud Task and requires **ZERO** IAM permissions to Cloud Storage.

```javascript
// HTTP Ingress Enqueueing the Task
const [signedUrl] = await file.getSignedUrl({
  version: "v4",
  action: "read",
  expires: Date.now() + 15 * 60 * 1000, // 15-minute validity matching Cloud Task TTL
});

enqueueValidationTask({
  tenantId: tenantId,
  blobId: blobId,
  payloadUrl: signedUrl, // Worker fetches this directly, bypassing IAM
});
```

#### Alternative: GCP Security Token Service (STS) Downscoping

If the worker must use Google Cloud SDKs natively instead of HTTP GETs, the worker must exchange its base Service Account token for a downscoped token using a **Credential Access Boundary**.

```javascript
// Inside the Background Worker
const { GoogleAuth } = require("google-auth-library");
const auth = new GoogleAuth();

// Define the absolute boundary: Worker can ONLY read this specific tenant's directory
const accessBoundary = {
  accessBoundaryRules: [
    {
      availableResource: `//storage.googleapis.com/projects/_/buckets/${BUCKET_NAME}`,
      availablePermissions: ["inAppPurchase.get", "storage.objects.get"],
      availabilityCondition: {
        expression: `resource.name.startsWith('projects/_/buckets/${BUCKET_NAME}/objects/ingestions/tenants/${task.tenantId}/')`,
      },
    },
  ],
};

// Exchange token via STS
const downscopedClient = await auth.downscopedClient(accessBoundary);
// Initialize Storage with the downscoped client
const storage = new Storage({ authClient: downscopedClient });
```

### 3.4 Firestore Tenant Ledger Validation

Even with a downscoped storage token, the worker must update the status in Firestore.
The worker MUST independently verify that it is updating a record within the correct tenant's ledger.

```javascript
// Worker Status Update
const jobRef = firestore
  .collection(`tenants/${task.tenantId}/jobs`)
  .doc(task.blobId);

await firestore.runTransaction(async (t) => {
  // Implicitly scoped to task.tenantId.
  // It is impossible for the worker to overwrite Tenant B's ledger using Tenant A's Task Payload.
  t.update(jobRef, { status: "COMPLETED" });
});
```

## 4. Rollout Plan

1. **IAM Revocation:** Remove `roles/storage.objectViewer` from the Cloud Run Worker service account.
2. **Ingress Update:** Update the HTTP ingress to namespace storage paths, generate Pre-Signed URLs, and sign Claim Checks using a secure, rotated `CLAIM_CHECK_SECRET`.
3. **Worker Update:** Update workers to fetch payloads via the Pre-Signed URL instead of using the Google Cloud Storage SDK.
4. **API Update:** Update the polling endpoint to verify the JWT Claim Check and assert tenant ownership.
