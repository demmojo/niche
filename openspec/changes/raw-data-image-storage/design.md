## Context

When users upload an image (e.g. a screenshot) to the Raw Data Library, they expect the image to be permanently attached to that data source. Currently, the upload merely parses the image locally to Gemini, extracts data, and saves a local, temporary filename (e.g., `pasted-image-....png`). Because this path is ephemeral and inaccessible to anyone else (or even the same user on a different device or later session), the images appear as broken links and cannot be downloaded.

We need to fix this broken experience. Our primary stack utilizes Firebase for Authentication and Firestore (user data), while Supabase handles data assets (`raw_data_assets`) via edge functions/APIs. We explored several storage solutions.

## Goals / Non-Goals

**Goals:**

- Enable persistent storage for user-uploaded images in the Raw Data Library.
- Allow users to view these uploaded images reliably across sessions.
- Provide a clear, accessible way for users to download their uploaded images.
- Standardize all Raw Data Library blob storage on Supabase.

**Non-Goals:**

- Build complex edge functions or syncing mechanisms between Firebase Auth and Supabase Storage.
- Support massive file uploads or file types beyond images for this specific feature.
- Retroactively fix broken images from past user sessions (since the data is lost).

## Decisions

**1. Use Supabase Storage for Images**

- **Decision**: We will use Supabase Storage to persist the images uploaded via the `UploadDataModal`.
- **Rationale**: The Raw Data Library architecture already uses Supabase for storing versions and assets. Using Supabase Storage for the associated image blobs ensures architectural consistency and keeps all raw data assets in one place. We will leverage the newly implemented Firebase Auth to Supabase JWT bridge for secure access.
- **Alternatives Considered**:
  - _Firebase Storage_: Initially considered because users authenticate via Firebase. However, this fragments the Raw Data Library architecture (tabular data in Supabase, blobs in Firebase). The JWT bridge makes Supabase Storage viable and secure.
  - _Base64 Encoding in Firestore_: Firestore has a strict 1 MiB document limit. Uploading large strings via Base64 would rapidly hit those limits and incur high bandwidth costs, leading to poor performance.

**2. Store Compressed Images**

- **Decision**: We will upload and store the compressed version of the image (generated by the existing `compressImage` utility) rather than the original high-resolution file.
- **Rationale**: The compressed version is already sufficient for both AI analysis and UI previews. Storing the compressed image saves bandwidth, accelerates uploads, and reduces cloud storage costs.

**3. Client-Side Upload Architecture**

- **Decision**: The React client will handle the direct upload to Supabase Storage.
- **Rationale**: This is the fastest and simplest approach. It natively utilizes the user's Supabase client (initialized with the Firebase JWT) and RLS security rules without requiring an intermediate server proxy.

**4. Download UX**

- **Decision**: Add a Download button next to the Maximize button on the image hover state within the `DataSourceCard`.
- **Rationale**: This provides immediate access to the download action without requiring users to open a detailed modal, keeping the workflow efficient.

## Risks / Trade-offs

- **Risk: Supabase Storage Setup** -> The project needs a configured Supabase Storage bucket (e.g., `raw-data-images`) and appropriate RLS policies tied to the `team_id`.
- **Mitigation**: Create the bucket and define RLS policies ensuring users can only read/write images within their `team_id`.

- **Risk: Cross-Origin Resource Sharing (CORS)** -> Downloading images from a different origin can sometimes cause the browser to open the image in a new tab rather than downloading it directly.
- **Mitigation**: We will use a programmatic fetch in React to download the blob and trigger a local download using an anchor tag (`<a download>`), ensuring a consistent download experience. We must also configure CORS on the Supabase Storage bucket.
