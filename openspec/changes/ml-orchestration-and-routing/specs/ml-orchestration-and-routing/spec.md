# Specification: ML Orchestration & Prompt Engineering\n\n## Detailed Features\n\n### 1. Smart Routing Interface\nThe `aiClient.ts` module will accept a `Capability` enum instead of a model name.\n\n### 2. Backward-Compatible API Migration\nThe new system exposes `/v2/orchestrate` returning HTTP 202 and a Job ID. Existing `/v1/` sync endpoints remain intact but internally await the queue result, ensuring legacy clients do not break immediately.\n\n### 3. Queue Architecture\nIntegration of BullMQ via Redis for persistent, distributed task execution, replacing `p-queue`.\n\n## Scenarios\n\n**Scenario 1: High-volume data extraction**\n* **WHEN** the system requests a task with `capability: 'extraction'` and `complexity: 'low'`\n* **THEN** the orchestrator routes the request to `gemini-3.1-flash-lite-preview`\n* **AND** execution is safely managed and throttled via a persistent Redis queue (BullMQ).\n\n**Scenario 2: API Backward Compatibility**\n* **WHEN** a legacy client requests an ML generation via the `/v1/` synchronous endpoint\n* **THEN** the server enqueues the job and synchronously polls internally until completion\n* **AND** returns the expected immediate JSON response without breaking the client contract.\n\n**Scenario 3: Rate Limiting Safety (No Escalation)**\n* **WHEN** the API returns an HTTP 429 Rate Limit error\n* **THEN** the client performs an exponential backoff with jitter\n* **AND** if retries are exhausted, it returns a 429 failure to the client rather than escalating to a Pro tier, preventing cascading cost and limit violations.\n\n**Scenario 4: Pro Tier PLG UX**\n* **WHEN** a task routes to the high-latency Pro Tier\n\* **THEN** the front-end receives staggered asynchronous progress updates via SSE/WebSockets tied to the BullMQ job.
