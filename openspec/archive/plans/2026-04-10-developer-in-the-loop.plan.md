# OpenSpec Plan: Developer in the Loop (CLI & Agent Refactor)

## 1. Context & Problem Statement

Currently, Cursor agents execute OpenSpec CLI commands (like `propose`, `start`, and `archive`) using `--non-interactive` and `--force` flags to avoid terminal hangs. While this prevents the AI from getting stuck on user prompts, it results in a "black box" execution model where agents modify critical architecture files (`openspec/*`), trigger auto-fixes, and bypass developer oversight.

We must refactor this to keep the developer in the loop without removing `--force` and `--non-interactive` globally, as banning those flags would permanently break headless CI/CD pipelines, stochastic evaluations, and the `start --auto-fix` self-healing loops mandated by our `AGENTS.md` rules.

## 2. Objective

Refactor the OpenSpec CLI and Cursor Agent rules/skills to enforce a **Dual-Mode Execution Architecture**:

1. **Interactive Agent Mode:** Agents must preview changes safely via `--stage` and present the `FsIntent` to the developer. The developer must approve the changes before the agent can execute the apply command.
2. **Headless CI/CD Mode:** Automated pipelines and internal auto-fix loops retain the ability to use `--force` to bypass staging and apply changes atomically.

## 3. Architecture & Implementation Design

### 3.1. Intent-Based Execution & Staging (`--stage` flag)

To prevent agents from modifying the DAG silently, we introduce a token-gated staging workflow.

- **Feature:** Mutative commands (`start`, `propose`, `archive`) receive a `--stage` flag.
- **Behavior:** `npm run openspec <cmd> --stage` computes the required changes without mutating the active DAG. It writes generated artifacts to a scoped `.tmp/openspec_<token>/` directory and runs validations (`dag`, `ai-eval`) against this staged state.
- **Output:** It writes a full unified diff to `.tmp/intent_<token>.patch`. It outputs a lightweight metadata summary to `stdout` (e.g., `[{"action": "overwrite", "file": "spec.md", "lines": "+150/-20"}]`) along with a unique execution hash (`commit_token`).
- **TOCTOU Protection:** The `commit_token` is generated by hashing ONLY the specific working directory files affected by the `FsIntent`. Hashing the entire `openspec/` directory is an anti-pattern that would cause false-positive drift rejections due to unrelated background saves.

### 3.2. Chat-Gated Application (The Soft Boundary)

To physically prevent Time-Of-Check to Time-Of-Use (TOCTOU) vulnerabilities:

- **Execution:** The command `npm run openspec apply --token=<commit_token>` validates the drift hash against the specific targeted files and performs a leaf-level atomic swap (write-replace) of the staged `.tmp` files into the active `openspec/` directory.
- **Agent Constraint:** We acknowledge that passing the token via `stdout` creates a "Chat-Gated Soft Boundary" reliant on strict prompting. The agent will hold the token in memory and prompt the user: _"Please review \`.tmp/intent\_<token>.patch\`. Reply 'approve' to execute."_
- **Context Recovery (`openspec status`):** Relying on an LLM to hold a specific UUID in chat memory is extremely fragile. If the user asks a tangential question during review, the context window shifts, causing token hallucination. We introduce `npm run openspec status` to list pending staged patches in `.tmp/` and deterministically recover active `commit_tokens`.
- **Preservation & Hygiene:** If validation fails, `.tmp/` is preserved for native IDE inspection. A cleanup function will purge `.tmp/` artifacts older than 24 hours to prevent workspace bloat.

### 3.3. Dual-Mode `auto-fix` Escape Hatch

- **CLI Behavior:** Deprecate _implicit_ `start --auto-fix`. The CLI must halt and return a strict failure code if a spec is out of sync.
- **Agent Behavior:** The agent is instructed to run `start --auto-fix --stage` to compute the self-healing corrections, but MUST require developer approval via the `apply` command to write the fixes.
- **CI/CD Bypass:** In headless CI/CD environments (e.g., GitHub Actions), `--force` remains valid and bypasses the `--stage` requirement entirely, fulfilling the rules laid out in `AGENTS.md`.

### 3.4. Claude Code Native Hooks vs Cursor Compatibility

- **Vendor-Lock Rejection:** Claude Code provides proprietary `PreToolUse` hooks that natively intercept CLI tools and prompt humans via TTY (`Y/n`). However, Cursor IDE does not support these proprietary Anthropic hooks. Relying on them would break the agentic workflow in Cursor.
- **Architectural Decision:** We explicitly reject relying on Claude Code native hooks. The custom Two-Phase Commit architecture (`--stage` then `apply --token`) remains the environment-agnostic standard, gracefully degrading across Cursor, headless CI/CD, and standalone terminals.

### 3.5. Future-Proofing: MCP Wrapping (Solving Schema Hallucinations)

- **Feature:** While the CLI executes the bash commands, the string-based parsing is prone to hallucination.
- **Behavior:** The OpenSpec CLI logic will be wrapped inside a Model Context Protocol (MCP) server. The MCP server will expose strongly typed tools: `openspec_stage`, `openspec_status`, and `openspec_apply`. This eliminates CLI syntax hallucinations while preserving the underlying Two-Phase Commit staging mechanics.

## 4. Execution Tasks

### Phase 1: CLI Core Refactor (Dual-Mode Execution)

- [ ] **Task 1.1:** Refine `FsIntent` / `FsExecutor` to support `GitMoveIntent` specifically for `archive`, and implement the `--stage` flag to write artifacts to a token-scoped `.tmp/openspec_<token>/` directory.
- [ ] **Task 1.2:** Implement the `commit_token` generation, hashing ONLY the specific working directory files affected by the `FsIntent` to prevent TOCTOU drift. Write the full unified diff to `.tmp/intent_<token>.patch`.
- [ ] **Task 1.3:** Update `TerminalPresenter` to emit a lightweight, parseable JSON array of `FsIntent` summaries and the `commit_token` to `stdout`.
- [ ] **Task 1.4:** Create the `apply --token=<token>` command that validates the targeted drift hash and executes the atomic leaf-level swap (write-replace). Ensure `--force` allows immediate application in CI/CD.
- [ ] **Task 1.5:** Create the `status` command to read `.tmp/` and list pending staged patches, allowing agents to deterministically recover lost tokens. Ensure `.gitignore` tracks `.tmp/` and implement a pre-stage cleanup function to purge artifacts older than 24 hours.

### Phase 2: Agent Tooling & Rules Refactor

- [ ] **Task 2.1:** Update `openspec-workflow.mdc` to explicitly define the Dual-Mode Execution Architecture. Forbid agents from using `--force` or implicit auto-fixes without prior chat approval, while preserving `--force` for headless pipelines. Instruct agents to use `openspec status` if they lose context.
- [ ] **Task 2.2:** Update `.cursor/skills/create-openspec/SKILL.md` and `.cursor/skills/apply-openspec/SKILL.md` to implement the "Agent-as-Partner" UX flow where the agent stages, waits for natural language "approve", and applies.
- [ ] **Task 2.3:** Update `.cursor/skills/archive-openspec/SKILL.md` to include identical confirmation gates and explicit handling of the `GitMoveIntent` abstraction. (Note: `extract-lessons/SKILL.md` operates on `AGENTS.md` standard file writes and does not require `GitMoveIntent`).
- [ ] **Task 2.4:** Update `AGENTS.md` to document the Dual-Mode pattern, the `status` recovery loop, and the explicit rejection of Claude Code hooks in favor of Cursor compatibility.

### Phase 3: MCP Server Wrapper

- [ ] **Task 3.1:** Scaffold a local MCP server (`openspec-mcp`) that imports the existing CLI Node.js modules.
- [ ] **Task 3.2:** Expose three strictly typed tools: `openspec_stage` (accepts DAG options), `openspec_status` (returns pending tokens), and `openspec_apply` (accepts token).
- [ ] **Task 3.3:** Configure the workspace to load this MCP server natively, removing the reliance on standard Bash execution for these specific commands.
