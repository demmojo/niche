# OpenSpec Plan: CLI Robustness Hardening

## 1. Context & Objective

The OpenSpec CLI currently suffers from several structural vulnerabilities during edge-case executions, including orphaned Git worktrees, metadata data loss during legacy migrations, brittle handling of empty commits, unhandled `EPIPE` exceptions in piped CI environments, and dependency resolution conflicts caused by `node_modules` symlinking. This plan resolves these issues by implementing transactional staging directory backups, index-aware git validation, and strict isolation boundaries.

## 3. Design & Architecture

### 3.1 Worktree Teardown & EBUSY Abandonment

Instead of relying on `fs.rmSync` followed by `git worktree prune`, the CLI will use Git's `child_process.spawn` (or `execFile`) with `shell: false` and the double-dash `--` convention (e.g., `spawn('git', ['worktree', 'remove', '--force', '--', targetPath])`). All external commands MUST be executed using `child_process.spawn` or `spawnSync` with `{ shell: false }`; `exec` and `execSync` are strictly forbidden.. Because background daemons (e.g., TS Server, ESLint) often lock files inside the worktree (triggering `EBUSY` or `EPERM` on Windows/macOS), Git will exit with a non-zero status code and write to `stderr`. The teardown sequence MUST rely entirely on standard OS-level or Node.js filesystem error codes (`EPERM`, `EBUSY`) or the subprocess exit codes, rather than brittle substring matching of English words in `stderr`, to differentiate expected OS locks from fatal errors. If an `EBUSY` lock is encountered, the CLI will simply abandon the directory in place without attempting to rename or move it, logging a non-fatal warning. This ensures the execution loop completes instantly without throwing `EPERM` on locked directories. Strictly use `git worktree remove --force <path>` as the sole teardown mechanism. Only fallback to physical deletion followed by `git worktree prune` in future boot-time sweeps if the `remove` command explicitly failed due to OS-level lock (`EBUSY`) restrictions.

### 3.2 Idempotent Auto-Recovery via Atomic Staging

To prevent split-brain states and eliminate the need for complex Write-Ahead Logs (WAL) or rollback ledgers, the CLI will embrace **Atomic Directory Swapping**. All AI-generated scaffolding, file mutations, and staging operations MUST occur strictly within an isolated `.tmp/[ExpiryTimestamp]-[UUID]` staging directory. Crucially, the CLI will NEVER mutate the live workspace incrementally. Once the staging directory is fully built, validated, and hashed, the `swapStagingToLive` will execute a single, instantaneous OS-level `fs.renameSync` to swap the staged assets into the live workspace. For individual files, `fs.renameSync` provides O(1) atomicity. For non-empty directories like `node_modules`, the CLI acknowledges that true O(1) atomicity is impossible via POSIX rename due to `ENOTEMPTY`. To execute the final atomic swap over a populated workspace, the CLI MUST first rename individual active directories (like `node_modules`) to a unique `.tmp/node_modules_old_[UUID]` suffix (where `[UUID]` is strictly generated via `crypto.randomUUID()` to prevent predictable path creation and `ENOTEMPTY` blocking attacks), then rename individual directories from the staging directory into their respective original live workspace paths, and finally asynchronously delete the old workspace. This guarantees POSIX atomicity for the entire project state without throwing `ENOTEMPTY` or `EBUSY`. If interrupted during this sequence, the next boot-time sweep MUST explicitly detect orphaned `_old` directories or files. To prevent split-brain state corruption from concurrent local CLI executions (e.g., a developer rapidly triggering the CLI in multiple terminal tabs), the recovery routine MUST first acquire a local atomic lock (e.g., using POSIX advisory record locking (e.g., `fs-ext`'s `flock` or `lockf` on a `.openspec-recovery.lock` file)). To prevent deadlocks if the crash-only CLI is SIGKILLed while holding the lock, it MUST implement native OS-level file locking (e.g., using `fs-ext` or standard `fs.open` exclusive flags) which guarantees the operating system automatically releases the lock if the process dies via `SIGKILL` or OOM, completely eliminating brittle time-based heuristics. Once securely locked, the recovery routine MUST verify if the live workspace is already successfully populated with the new state (e.g., via hash parity), specifically checking for a deterministic "half-swapped" state indicator (e.g., an explicit `.openspec-swap-in-progress` marker file created _before_ the 3-step directory rename begins). This gives the boot sweep absolute certainty to either roll forward (by moving the remaining directories in) or roll backward (by moving the `_old` directories back) if the workspace was interrupted mid-swap, before deleting the marker file. If the new state is fully applied, it simply deletes the orphaned backups. If the live state is missing or corrupted, it restores the backups to the live workspace path to prevent data loss. This recovery MUST occur before any other operations. This guarantees true O(1) atomicity and idempotency. If the CLI crashes, is SIGKILLed, or fails validation _before_ the final atomic swap, the live workspace remains completely untouched. The abandoned `.tmp/` directory simply becomes orphaned and is cleanly swept by the background garbage collector. The system is inherently self-healing and crash-immune. In headless environments (detected via `process.env.CI`), the CLI will bypass automatic stagings and interactive recovery, opting to fail hard and freeze the staging directory state. To ensure deterministic CI artifact inspection and debugging, the frozen staging state will be dumped to a predictable `.openspec-failed-artifacts/` directory within the local workspace (rather than the ephemeral `.tmp/` staging directory).

### 3.3 Process Lifecycle & Terminal Isolation

Trapping `SIGINT` (Ctrl+C) for heavy synchronous file I/O stagings frustrates users and escalates to untrappable `SIGKILL`s. The CLI will **not** trap termination signals for stagings. It will embrace a true crash-only design, letting the process die instantly on `SIGINT` (Ctrl+C), `SIGKILL`, or OOM, relying on the asynchronous boot-time sweep to automatically clean up partial states on the next boot (with a narrow exception for secure credential unlinking).. The CLI will globally attach `EPIPE` swallow handlers to `process.stdout` and `process.stderr` to prevent downstream pipe closures (e.g., `openspec ... | jq`) from crashing the process.

To protect against downstream webhook limits crashing due to massive diffs, the CLI will use a simple `StdioRouter` module to strictly enforce that all human-readable logs route to `stderr`, reserving `stdout` exclusively for valid JSON payloads. If `--payload-dump-dir=<path>` is provided, the CLI will ALWAYS emit the `{ "payloadDumpPath": "..." }` reference to `stdout` regardless of payload size to maintain a deterministic type signature. To prevent V8 memory bloat and event loop blocking, the `StdioRouter` will leverage the Payload Dump pattern. Because the Payload Dump inherently caps the stdout payload size (to a tiny 50-byte string like `{"payloadDumpPath": "..."}`), forcing `JSONStream` or `bfj` is extreme over-engineering. While emitting the tiny 50-byte `{"payloadDumpPath": "..."}` to `stdout` via standard `JSON.stringify` is perfectly safe, the CLI MUST use an asynchronous or streaming JSON serializer strictly when writing the actual large payload (e.g., 50MB) to the dump file on disk, preventing the main Node.js event loop from blocking for hundreds of milliseconds. If the payload exceeds 100KB and the flag is NOT provided, the CLI will enter a deprecation phase where it emits a high-visibility warning to `stderr` and proceeds to emit the large payload to `stdout`, rather than throwing an immediate fatal error. Strict fatal enforcement will follow in the next major version. This prevents schema mutation breakages for downstream consumers. The `--payload-dump-dir` argument must be strictly validated by Zod to prevent directory traversal payloads (e.g., `../../`). To support CI environments without opening sandbox escapes, this specific flag will strictly restrict absolute paths to a hardcoded allowlist of safe base directories. To prevent Local Denial of Service via pre-created paths, use `fs.mkdtemp` to generate randomized, unpredictable paths (e.g., `/tmp/openspec-claims-[random]`). The CLI MUST use `fs.mkdtemp` to create a new directory with strict `0700` permissions, preventing TOCTOU hijacking by a malicious user in a shared /tmp/ environment. To securely prevent TOCTOU symlink traversal attacks where an intermediate directory is swapped with a symlink during resolution, the CLI MUST reject any paths containing symlinks entirely, or iteratively resolve and enforce `mkdir` on every segment of the path sequentially to ensure no intermediate symlinks are injected. The final physical path MUST exactly start with the `allowedBase` and a `path.sep`. The emitted path must be fully resolved to an absolute path. To prevent symlink traversal attacks within shared allowlist directories (like `/tmp`), the `StdioRouter` MUST open the file using the `wx` flag (`O_EXCL | O_CREAT`), forcing the OS to fail immediately if the file or a symlink already exists. The CLI MUST append a cryptographically secure UUIDv4 to the generated payload dump filename to prevent `EEXIST` crashes. Before generating the final path, it MUST explicitly sanitize and validate that the generated path components contain only safe alphanumeric characters and hyphens to prevent downstream Bash shell injection vulnerabilities (e.g., if a user scripts `eval $(jq -r .payloadDumpPath)`). To prevent Denial of Service (DoS) via unbounded payloads, the CLI MUST enforce a hard 50MB byte-size ceiling on the payload serialization stream, throwing `E_PAYLOAD_TOO_LARGE` if breached. To prevent silent disk inode exhaustion on long-living headless CI runners, the directory MUST be configured as an OS-level `tmpfs` or implement a strict explicit TTL garbage collection policy.

### 3.4 Strict Dependency Boundary (No Symlinking)

Monolithic or shallow symlinking of `node_modules` into worktrees poses severe risks of root-workspace corruption via NPM traversal and "Invalid Hook Call" singleton duplications. The `node_modules` symlink and any reliance on `NODE_PATH` injection will be completely eradicated.

Instead, to maximize cross-platform reliability and eliminate branching complexity based on OS file systems, the CLI will implement Conditional Dependency Hydration. It will only execute a bounded `npm ci --prefer-offline --no-audit --ignore-scripts --fund=false` if the combined SHA-256 hash of `package.json` and `package-lock.json` differs from a cached `.openspec-deps-hash` file stored in the `.openspec/` cache directory. This is deterministic, Git-immune, and `O(1)` to check. If untouched and the `node_modules` directory exists, hydration is safely skipped to avoid massive I/O bottlenecks. If `node_modules` is missing, the CLI executes `npm ci`. The AI MUST NEVER mutate `package-lock.json` directly. If `package.json` drifted, the CLI executes `npm install --ignore-scripts --no-audit --fund=false` to natively and securely regenerate the lockfile within the staging directory. To prevent lockfile path corruption, the CLI MUST dynamically rewrite local `file:` or `workspace:` relative paths to absolute paths bounded by `resolveConfinedPath` before executing `npm install`, and explicitly revert them to their original relative structure in the generated `package-lock.json` before swapping it into the live workspace. To prevent V8 memory bloat and Event Loop starvation on massive enterprise lockfiles, the CLI MUST use a streaming JSON transformer or a `readline` stream to mutate these paths on-the-fly, strictly forbidding synchronous `JSON.parse()` on the entire AST. This ensures the package manager safely regenerates the lockfile natively before the atomic swap. To prevent silently clobbering manual edits, the CLI MUST use `fs.promises.open()` to acquire an immutable file descriptor handle, verify it is not a symlink via `handle.stat()`, and then stream directly from the handle into `crypto.createHash()` to prevent TOCTOU symlink swapping, explicitly rejecting abnormally large files to prevent V8 OOM crashes), and assert these hashes match the live files immediately before the final swap. If drift is detected, abort the swap. Then execute a sequence of asynchronous `fs.promises.rename` calls (wrapped in a concurrency limiter like `p-limit(100)` because `fs.rename` only updates directory indices and does not hold open file descriptors like `fs.open`, maximizing NVMe disk IOPS) to move individual mutated files and directories from the `.tmp/[UUID]` staging directory over the live workspace, guaranteeing POSIX atomicity for all files and dependencies simultaneously, avoiding split-brain state corruption.) to mutate dependencies without violating atomic isolation. This provides a single, predictable dependency staging path without requiring unreliable Copy-on-Write (CoW) feature detection or pre-compiled tarball management. Hard-linking is strictly forbidden to prevent sandboxed agents from modifying root dependencies via mutable inodes.

### 3.5 Ephemeral State & Explicit Recovery (Lockfile GC)

To prevent silent disk exhaustion and main-thread event loop blocking from hard crashes, the CLI will perform a fast, synchronous boot-time check strictly for unresolved staging states (blocking execution if found). To ensure this boot check does not degrade performance with a massive `.tmp/` directory, unresolved staging states will be explicitly namespaced (e.g., `.tmp/staging-[ExpiryTimestamp]-[UUID]`) and by performing a simple asynchronous boot-time sweep of expired directories. A strict `.openspec-recovery.lock` is used ONLY during the atomic boot-time recovery phase. All transient staging environments will be built locally within the workspace's `.tmp/` directory. Upon initialization, the CLI MUST automatically ensure `.tmp/` is appended to the workspace's `.gitignore`, `.eslintignore`, and `.prettierignore` (to prevent IDE lock contentions). Furthermore, the CLI MUST explicitly document that CI/CD cache definitions (e.g., GitHub Actions `actions/cache`) must exclude the `.tmp/` and `.openspec-failed-artifacts/` directories to prevent massive failed staging states from ballooning cache sizes and degrading CI performance. to prevent IDE language servers from aggressively indexing the thousands of files generated during staging, which prevents `EBUSY` lock contentions. Before creating the `[UUID]` subdirectory, the CLI MUST directly execute `fs.promises.mkdir(..., { recursive: true, mode: 0o700 })`, relying on the operating system's native atomic filesystem operations to handle existing directories securely, rather than introducing a TOCTOU vulnerability via `lstat` checks. and ensuring `fs.copyFile` utilizes flags that preserve the original file modes, moving away from the previously proposed `os.tmpdir()`.

If the asynchronous boot-time sweep detects orphaned staging directories, it will simply log a debug message and proceed with pruning them. To prevent concurrent "thundering herd" crashes in matrix CI pipelines, the recursive deletion routine will explicitly swallow `ENOENT`, `ENOTEMPTY`, `EBUSY`, and `EPERM` exceptions. Crucially, the CLI will **never silently delete `.tmp` staging directories on validation failures** (e.g., failed DAG checks); these will be renamed with a `failed-` prefix (e.g., `.tmp/failed-[ExpiryTimestamp]-[UUID]`) which the asynchronous boot-time sweep will explicitly ignore if recent. To prevent infinite unbounded disk bloat, the asynchronous boot-time sweep will enforce a strict TTL encoded into all directory names (e.g., `.tmp/[ExpiryTimestamp]-[UUID]`) using strict string splitting (e.g., `split('-')`) or regex with zero nested quantifiers to parse the filename structure, and validating that the `ExpiryTimestamp` is mathematically bounded (e.g., maximum 24 hours from current time). Anomalous, unparseable, or maliciously future-dated timestamps MUST NOT be ignored; the directories MUST be forcefully deleted to prevent DoS via disk exhaustion, preserving them long enough for forensic inspection before deterministic cleanup.

### 3.6 Strict Drift Detection & TOCTOU Prevention

To prevent Time-of-Check to Time-of-Use (TOCTOU) race conditions where files are modified between the `--stage` and `--apply` phases, the CLI will rely on cryptographic SHA-256 staging tokens rather than Git index mechanics (which are blind to human workspace edits made _before_ staging). To completely eliminate TOCTOU race conditions where files are modified between the hash validation and the Apply read, the CLI will pipe the exact in-memory validated byte buffer (used during the hash and secret scanning phase) directly into `` to ingest the blobs into the Git object database. In the `--apply` phase, the CLI will update the Git index directly using those exact blob IDs (`` via stdin stream), wrapping this operation in a retry loop with **jittered** exponential backoff (hard-capped at 5 retries and a 500ms maximum delay) specifically targeting `fatal: Unable to create '.../.git/index.lock': File exists` errors to ensure stability against IDE background watchers.. To prevent destroying uncommitted manual edits made during the TOCTOU window, the CLI will compare the working tree file hash (using native Node.js `crypto.createHash('sha256')` streams, completely eliminating `native Node.js filesystem hashing` pipeline deadlocks). To completely eliminate TOCTOU race conditions where files are modified between the hash validation and the Apply read, the CLI will ingest the files directly into the Git object database _during_ the hash phase using `-paths` (which returns the blob ID). In the `--apply` phase, the CLI will update the Git index directly using that exact blob ID (``), wrapping this operation in a retry loop with **jittered** exponential backoff (hard-capped at 5 retries and a 500ms maximum delay) specifically targeting `fatal: Unable to create '.../.git/index.lock': File exists`errors to ensure stability against IDE background watchers.  To prevent V8 OOM and disk exhaustion during the TOCTOU hash check phase, the CLI MUST implement a per-file size limit (e.g., 50MB), a global cumulative byte-size limit (e.g.,`MAX_TOTAL_PAYLOAD = 500MB`, strictly configurable via the `OPENSPEC_MAX_PAYLOAD_MB`environment variable), and wrap the hashing stream operations in a concurrency limiter scaled to the host's capabilities (e.g.,`p-limit(Math.max(4, os.cpus().length))`) to maximize NVMe SSD throughput without exhausting `EMFILE`limits. A running byte counter must track the total size of files staged, aborting the pipeline immediately if the cumulative threshold is breached. It must actively drain the child process`stdout`stream strictly in parallel with the`stdin`pipeline (e.g., using`Promise.all([stream.pipeline(...), consumeStdout(...)])`) to prevent OS IPC pipe buffer deadlocks. If `ENOENT` is thrown during the TOCTOU check (indicating a file was physically deleted mid-flight) or if hash drift is detected, the transaction will explicitly abort, prompting the user. It will never force-clobber the working directory.

### 3.7 Index-Aware Commit Gates

Relying on standard `git status --porcelain` mixes untracked and staged file states. The CLI will strictly use `git diff --cached --quiet` to determine if the _index_ is dirty before executing `git commit`, failing gracefully if empty.

To ensure commit hygiene without sacrificing performance or triggering interactive hooks, the CLI will execute `git commit` (respecting organizational hooks by default, with an `--ignore-hooks` opt-out). General code quality validation should be explicitly deferred or passed via fast native scanners, the CLI will implement a fast, native secret-scanning step _during the staging phase_, strictly before the atomic swap to the live workspace. To prevent V8 Out-Of-Memory (OOM) crashes and main-thread Event Loop starvation, the chunked line-by-line streaming secret scanner MUST be executed synchronously on the main thread using standard regex (or delegated to a highly optimized native binary like ripgrep) to avoid the premature abstraction, IPC overhead, and memory bloat of a `worker_threads` pool.. The scanner will utilize a fixed-window streaming scanner, fast entropy checks, or safely bounded JS regex (enforcing a sliding window chunking mechanism with overlap explicitly sized to exceed the maximum expected length of secrets (e.g., 2048+ characters) to prevent long secrets like RSA keys or JWTs from bypassing detection at boundaries, matching fixed prefixes like `sk_live_` first before evaluating regex, and prohibiting nested quantifiers, Because standard JS regex cannot be timed out on the main thread, the CLI MUST rely exclusively on pre-audited regex patterns with no nested quantifiers, or implement a state-machine/token-based scanner to guarantee no ReDoS vulnerability) to securely scan long lines (e.g., minified files) without ReDoS risks or arbitrary truncation blind spots, explicitly avoiding native C++ dependencies like `node-re2` to ensure cross-platform compatibility.. If a secret is detected, the CLI MUST loudly fail the execution with a terminal warning pinpointing the file and abort the staging process, guaranteeing the secret never enters the live workspace or Git index.

To prevent Denial of Service (DoS) memory exhaustion, the CLI MUST enforce a hard ceiling on the maximum number of changed/untracked files processed (e.g., `MAX_FILES = 25,000`, strictly configurable via the `OPENSPEC_MAX_FILES` environment variable for enterprise monorepos) via stream data chunking. If the limit is breached, abort immediately with an `E_TOO_MANY_FILES` error. Furthermore, when extracting paths during staging, the CLI will use `git diff --cached --name-only -z` and explicitly parse the null-terminated UTF-8 output. Because `--name-only` does not output status codes or `old_path` entries, the parser MUST split by `\0` and filter empty strings without attempting to skip `old_path` permutations.

### 3.8 Security & Credential Hygiene

To prevent accidental leakage of sensitive authentication tokens during automated staging, the CLI will **never** write `.npmrc` files containing secrets to the worktree disk. To prevent untrusted child processes from inheriting and exfiltrating credentials via `/proc/<pid>/environ` (which can leak to arbitrary child processes), the CLI MUST NOT inject tokens into the global `process.env`. The `env` object passed to `spawn` must explicitly omit sensitive inherited variables. Furthermore, the CLI MUST explicitly strip `NPM_CONFIG__AUTH` and any other sensitive `NPM_CONFIG_*` variables (like `NPM_CONFIG_TOKEN`) from the `spawn` environment. When spawning `npm ci`, the CLI MUST strictly validate any inherited `NPM_CONFIG_PROXY` or `NPM_CONFIG_HTTPS_PROXY` environment variables against trusted schemes (`http`/`https`) to prevent workspace proxy hijacking, rather than blindly wiping them (which would break legitimate corporate firewalls). The ephemeral `.npmrc` provisioner MUST map all supported legacy auth tokens (like `NPM_CONFIG_TOKEN`) to the standard `_authToken` configuration internally to prevent silent authentication breakages. to prevent token inheritance, while preserving legitimate enterprise configurations (like `NPM_CONFIG_PROXY` or `NPM_CONFIG_CAFILE`) required for `npm ci` execution behind corporate firewalls. Setting `NODE_OPTIONS=""` is forbidden as it strips valid `--max-old-space-size` limits. Because environment variables injected into `spawn` leak via `/proc/<pid>/environ`, the CLI MUST NOT write an ephemeral `.npmrc` file to physical disk. Instead, the CLI MUST securely provision it via `os.tmpdir()`. To prevent configuration precedence vulnerabilities where a malicious workspace-level `.npmrc` overrides the ephemeral config, the CLI must enforce `--userconfig=.npmrc` and explicitly run the `npm ci` process from within the staging directory (ignoring the workspace root entirely). However, to support enterprise monorepos relying on complex local `.npmrc` definitions for internal scoped packages, the CLI MUST dynamically parse and merge safe registry configurations from the workspace root `.npmrc` into the ephemeral `.npmrc` before spawning `npm ci` or `npm install`. Furthermore, to support native binary compilation (e.g., Prisma, esbuild), the CLI MUST provide an explicit `--allow-scripts` opt-in flag to safely bypass the default `--ignore-scripts` staging restriction when strictly necessary.

Furthermore, the CLI will strictly parse, validate, and type all CLI flags using **Zod schemas** at the application boundary, prohibiting the use of raw Commander `.opts()`. To prevent directory traversal and sandbox escapes, all path resolution within internal staging logic MUST utilize a rigorous `resolveConfinedPath` utility, enforcing absolute path confinement within the workspace boundaries (exempting explicit external paths passed to `--payload-dump-dir`).

Because `--name-only` does not output status codes or `old_path` permutations, the parser MUST NOT attempt to skip any strings, preventing valid changed files from being silently dropped. ## 5. API Contracts & Breaking Changes

To explicitly manage downstream impact, the following API contract changes are formalized:

- **Stdout Schema Mutation**: To prevent breaking downstream CI tools, the CLI will retain its plaintext/raw JSON default output behavior. The standardized wrapper schema `{ "data": <payload | null>, "payloadDumpPath": <string | null> }` is strictly opt-in via a distinct new `--format=v2` flag, explicitly introducing a legacy `--format=v1` default mode. This leaves the existing `--json` flag output perfectly flat and backward-compatible. Furthermore, `--payload-dump-dir` strictly REQUIRES the `--format=v2` flag. If `--payload-dump-dir` is provided without `--format=v2`, the CLI MUST throw a hard validation error (exit code > 0) immediately, explicitly rejecting the invalid flag combination.
- **Large Payload Fatal Errors**: Failing to provide `--payload-dump-dir` for payloads >100KB will emit a deprecation warning to `stderr` instead of throwing a fatal error for now. to protect downstream pipe limits.
- **Strict Zod Flags**: Commander `.opts()` is replaced by Zod schemas. During the deprecation phase, unknown flags and non-strict coercions will utilize `z.object().passthrough()` to emit `stderr` warnings, but the CLI MUST strictly use Zod's native `.strict()` parsing method to securely reject unknown flags, abandoning convoluted manual `.passthrough()` diffing and custom deprecation warning loops to prevent Prototype Pollution vulnerabilities and eliminate maintainability debt. Deprecation warnings MUST NOT be suppressed in CI environments to ensure maintainers have visibility into upcoming breaking changes. They will be emitted to `stderr` in a non-fatal way (exit code 0).
- **Native Dependency Scripts**: The CLI will now execute `npm ci` and `npm install` with `--ignore-scripts` by default to secure the staging environment. This is a **major breaking change** for consumer projects relying on `postinstall` scripts for native binaries (e.g., Prisma, esbuild, node-sass). These projects MUST now explicitly pass the `--allow-scripts` opt-in flag, or their builds will silently fail to compile during staging.
- **NPM Authentication**: Global environment variables (`NPM_CONFIG__AUTH`) are strictly ignored. If `NPM_CONFIG__AUTH` is present in the global `process.env`, the CLI will enter a deprecation phase: it will securely translate it to an ephemeral `--userconfig` file stored in the staging directory. A `stderr` warning is explicitly emitted. Hard failures will be introduced in the next major version, requiring users to pass tokens via explicit CLI arguments or secure IPC.
- **Stdout Logging Prohibition**: All human-readable diagnostics are forcefully routed to `stderr`. `stdout` is strictly reserved for JSON. This strict JSON contract applies ONLY when JSON format flags (like `--json` or `--format=v2`) are provided. If no JSON flags are provided, the CLI retains its legacy behavior of emitting human-readable plaintext to `stdout`.
