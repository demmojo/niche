# Raw Data Image Storage & Download Brainstorm

**Date:** 2026-03-19

## What We're Building

Currently, when users upload images via the `UploadDataModal` in the Raw Data Library, the images are sent directly to the Gemini AI using a local base64 or object URL preview. The resulting analysis saves the local filename (e.g., `pasted-image...png`) as the `sourceUrl` in the database. Because these local references do not persist across sessions and are inaccessible, the images display as broken links, cannot be maximized, and cannot be downloaded by the user.

We need to fix this by introducing persistent cloud storage for these images so they can be reliably viewed, maximized, and downloaded by users at any time.

## Why This Approach

The current stack utilizes Firebase for authentication and primary user data (Firestore), while Supabase is used specifically for the `raw_data_assets` storage backend and federated search capabilities.

We explored three architectural approaches for image storage:

1.  **Firebase Cloud Storage (Selected):** Best fit since the user is already authenticated via Firebase Auth, allowing native, seamless Security Rules integration (`allow write: if request.auth.uid == userId`) directly from the client.
2.  **Supabase Storage:** Requires a complex bridging mechanism because users log in via Firebase Auth; Supabase Auth would not natively recognize the user for Row Level Security (RLS) policies.
3.  **Base64 Encoding in Firestore:** An anti-pattern due to Firestore's strict 1 MiB document limit and high bandwidth costs.

By selecting Firebase Storage, we ensure a fast, secure, and native integration without architectural overhead.

## Key Decisions

1.  **Storage Backend:** We will use **Firebase Cloud Storage**.
2.  **Image Quality:** We will upload and store the **Compressed version** (generated by the existing `compressImage` utility) rather than the original high-res version. This saves bandwidth, reduces storage costs, and is already sufficient for AI analysis and UI previews.
3.  **Download UX:** We will add a **Download button** next to the Maximize button on the image hover state within the `DataSourceCard`. This provides quick access without requiring users to open a detailed modal.
4.  **Upload Architecture:** We will use a **Client-side Firebase Upload** approach. The React client will upload the compressed image directly to Firebase Storage, retrieve the public download URL, and use that URL as the `sourceUrl` when saving the data source to Firestore.
